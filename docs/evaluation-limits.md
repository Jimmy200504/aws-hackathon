# 離線評測框架的邊界

作者：timchen
證據檔：[`reports/llm-contribution-exploration.json`](../reports/llm-contribution-exploration.json)

這份文件記錄一個結構性限制：**目前的離線評測是重排（re-ranking）評測，不是檢索（retrieval）評測。**
任何「讓使用者看到本來看不到的職缺」的改進，在這個框架下量不出來。

這不是實作缺陷，是主辦方提供的資料形態決定的。但它會影響該投資哪些方向，所以值得寫下來。

## 評測實際在做什麼

`artifacts/temporal-eval.json` 的每一筆 case 來自一次真實搜尋事件：

```
query_id      q_ec98dd392cd425e0
query (ks)    '美語老師'
location_code ['100200']
candidates    19 筆      <- 來自 empStr，既有系統當次實際曝光的職缺
qrels         3 筆有標記   {71587447: 1, 75824821: 1, 79227821: 1}
label_policy  max(view=1, apply=2) in [search_time, search_time+30m]
```

`candidates` 是**既有 1111 系統當時給這位使用者看的清單**。評測問的是：把這 19 筆重新排序，被點擊／應徵的能不能排更前面。

所以有兩件事被固定了：

- **候選集不能增加。** 沒被曝光過的職缺永遠不會出現在候選裡，也永遠不會有標記。
- **候選集已被舊系統過濾。** 舊系統依 query 與地區條件篩選過，所以候選集內部的同質性很高。

## 兩個實測案例

### 地理鄰接推薦：候選集裡沒有跨區職缺

想法是建立行政區相鄰圖，除了使用者指定的地區，也推薦相鄰地區的職缺。

在 confirmation 窗口實測（500 個 query）：

| | 數量 | 佔比 |
|---|---:|---:|
| 有帶 `location_code` 的 query | 385 | 77.0% |
| 這些 query 的候選職缺總數 | 6,620 | |
| 其中屬於「非指定城市」 | **7** | **0.1%** |
| 相關職缺（grade > 0）總數 | 1,027 | |
| 其中屬於「非指定城市」 | **2** | **0.2%** |

候選池裡幾乎不存在跨區職缺可以被「優先推薦」。就算鄰接圖完全正確，最多影響 2 筆相關職缺，NDCG@10 的變化落在小數第四位。

更強的說法是變異數而不是佔比。同一份 test split，把候選職缺對照 `職缺.csv`「工作城市」解析成縣市後：

| | test | validation |
|---|---:|---:|
| 可解析成國內縣市的 query | 383 | 380 |
| **候選只落在 ≤1 個縣市的 case** | **323 / 383（84.3%）** | 316 / 380（83.2%） |

（383 與上表 385 的差別是兩筆 `location_code` 為海外代碼，無對應國內縣市。）

超過八成的 case，所有候選職缺同屬一個縣市。縣市層級特徵在這些 case 的候選組內**取值恆定**，決策樹無法用它分裂 —— 效果不是小，是數學上為零。這個限制與圖的正確性無關，換成任何縣市層級訊號都一樣。

還有一個粒度問題：`location_code` 是區級（`100217` → 三峽區），但職缺的 `city` 欄位只有縣市級（distinct 值僅 27 個）。區級的相鄰關係在職缺側沒有可比對的資料。

後續在縣市層級改以**行為**建圖（不用地圖鄰接），產出 `artifacts/region-graph.json`，schema 與遍歷 trace 見
[`docs/graph-schema.md`](graph-schema.md) 的 Region subgraph 一節。該圖解決了「權重從哪來」的問題（201 條可替代邊與 62 條通勤邊全部來自 2,248,053 次搜尋與 121,419 筆應徵，無人工權重），但**沒有**解決上述變異數問題：它的作用位置在檢索擴充，不在重排。因此它不進 release gate，只作為圖譜能力與可解釋性的展示。

### 技能解析改善：訊號落在錯的候選上

Bedrock 查詢正規化把口語簡寫補成 ontology 詞彙，改寫品質良好：

```
貨車    -> 貨車司機          解析出的技能命中數 0 -> 10
小貨車  -> 小貨車司機         0 -> 10
大貨車  -> 大貨車司機         0 -> 13
接送    -> 接送司機           0 -> 8
711     -> 7-Eleven 門市人員   0 -> 17
水電    -> 水電技術員         0 -> 1
```

test split 有 143/499（28.7%）的 query 被改寫，但只有 **12 筆（2.4%）**真的改變了圖譜特徵。
那 12 筆裡 9 筆的預測排序確實改變了，但結果是：

| 結果 | 筆數 |
|---|---:|
| NDCG 上升 | 1 |
| NDCG 下降 | 3 |
| NDCG 不變 | 8 |

整體 NDCG@10：`0.4472 → 0.4469`，**−0.06%**。

不變的四種原因：

1. **已達天花板** — 唯一的相關職缺原本就排第一（`711`，NDCG 1.0000 → 1.0000）
2. **訊號沒落在相關職缺上** — `外場餐飲人員` 的 4 個相關職缺一個都沒拿到新訊號，被重排的是不相關的餐飲職缺
3. **名次沒實質移動** — 相關職缺拿到訊號、排序有變，但停在同一個名次區間
4. **訊號均勻** — 20 個候選拿到相同的特徵值，相對順序無法改變

下降的原因是訊號精準度不足：只有 **12/32（37.5%）**的相關職缺拿到新訊號，其餘 62.5% 沒拿到，而部分不相關職缺拿到了。訊號同時扮演證據和噪音。

## 共同根因

兩個案例的瓶頸相同：**候選集的同質性 + 職缺側邊的稀疏性**。

```
查詢側   使用者口語 -> ontology 節點      品質良好
職缺側   ontology 節點 -> 具體職缺        只覆蓋 6.5% 的候選職缺
```

查詢側補對了詞，下游沒有足夠的邊可以走。而候選集本來就是同一職業的職缺，所以就算補對了，也不具區辨力。

## 對投資順序的影響

**有依賴關係，不是平行選項。**

放大 train-only JD 抽取（提高職缺側覆蓋率）是量測查詢正規化的**前置條件**。順序顛倒必然測不到效果 — 這正是上述實驗的結果。

**離線指標不是唯一有效的證據形式。**

「提升召回」這類改進需要在全量檢索階段展示。目前 `app/retrieval.py` 的 OpenSearch 路徑對 1,218,635 筆職缺做 BM25，那才是候選集可以真正變寬的地方。在重排階段量測召回改善是類別錯誤。

**負面結果應該保留。**

`reports/llm-contribution-exploration.json` 記錄了兩個 arm 的探索結果（+1.00% 與 −0.06%，兩者信賴區間都跨零）與一個方法論錯誤的修正。這些數字不足以支持任何發布宣稱，樣本量與 bucket 的限制都寫在該檔的 `why_this_is_not_release_evidence` 欄位。

### 行政區 occurrence 判斷：通過驗證集不等於能用

證據檔：[`reports/district-collocation-effect.json`](../reports/district-collocation-effect.json)、
[`reports/district-collocation-judgement.json`](../reports/district-collocation-judgement.json)

抽取器的 surface 層閘門處理不了 occurrence 層的錯誤：`北區業務` 與 `北區和緯路` 共用同一個 surface，
精確度 4.66% vs 80.50%，沒有任何門檻切得開。用 LLM 逐處判斷是很自然的下一步，
而且**有 511 筆用實測誤留率標好的 collocation 可以先量準確率**，這是很少見的好條件。

流程照做了：先在標註集上量，第一版 prompt 只有 **66.54%**，被 `--min-accuracy` 擋下沒有進到套用階段。
診斷後改寫（原本問「這個字串文法上是不是行政區」，改成問「能不能據此推斷職缺所在地」），
並把 511 筆切成 dev / holdout 兩半，只在 dev 上調 prompt。第二版 dev **89.50%**、holdout **87.18%**，
過關。

**然後套用到 2,558 筆中間帶，發現那個 87.18% 不能外推。**

| 母體 | 判 place 的加權精確度 | 判 not_place 的加權精確度 | 分離度 |
|---|---:|---:|---:|
| 已標註 511 筆 | 0.9511 | 0.1197 | **0.8314** |
| 中間帶 2,558 筆 | 0.7792 | 0.6920 | **0.0872** |

**原因是結構性的。** 標註帶就是用誤留率切出來的（≤3% 標 place、≥50% 標 not_place），
所以它們**依定義**就是可分的簡單案例。中間帶之所以沒有標註，正是因為同一個量在那裡分不開 ——
而中間帶就是引入模型的全部理由。在能打分的母體上表現很好，不構成可以套用到分不開的母體的授權。

具體後果：477 個 collocation（26,811 筆比對）被判 not_place，但實測精確度 > 0.60，
包括 `南區) 0.6023`、`中區) 0.7635`、`東區) 0.8442`、`信義店) 0.8989`。
規劃時當作亮點的 `北區和緯`（0.8050）也被判成 not_place —— **模型在 occurrence 層重現了 surface 層的錯誤答案。**

三個 arm 的端到端結果：

| | 職缺數 | 覆蓋率 | 單一行政區佔比 |
|---|---:|---:|---:|
| surface 層閘門（現況） | 255,119 | 26.53% | 86.71% |
| **＋511 筆實測標註** | **256,014** | **26.62%** | 86.75% |
| ＋511 筆標註＋2,558 筆模型判定 | 254,369 | 26.45% | 87.00% |

**採用中間那列，不採用模型判定。** occurrence 層機制本身是對的（+895 筆職缺、覆蓋率與純度都升），
但驅動它的是實測標註，不是模型輸出。加上模型判定後覆蓋率反而掉回 baseline 以下。

**根因不是 prompt 寫得不好。** collocation 的 key 是 surface 後面**一個**漢字，
那對簡單案例夠、對模稜兩可的案例不夠 —— `南區)` 這四個字裡沒有能判定的資訊，換誰判都一樣。
要解這個中間帶得換特徵（整段職缺文字、地址欄位），不是換模型或換提示詞。

留下來的東西：`--collocation-judgements` 旗標預設關閉，
`reports/job-district-extraction.json` 與所有引用它的數字都沒有變動。

## 已知的方法論陷阱

**在你要評分的同一批資料上調提示詞會失敗。**

第一版 prompt 66.54% 之後，我看了全部 511 筆的錯誤才改寫第二版。這代表如果直接拿全部 511 筆重測，
那個分數描述的是調校過程而不是能力。因此把 511 筆用 key 的 hash 切成固定的 dev / holdout 兩半，
之後只看 dev 的錯誤，holdout 只在定稿後測一次（`scripts/judge_district_collocations.py --split`）。

dev 89.50% 對 holdout 87.18%，差距 2.3 個百分點，代表第二版沒有嚴重過擬合 dev。
**但要誠實記一筆：第二版的改寫方向來自看過全部 511 筆的錯誤，所以 87.18% 仍偏樂觀，應視為上界。**
真正乾淨的估計需要一批從未看過的標註，而那批不存在。

這一點最後沒有影響結論 —— 決定不採用模型判定的理由是中間帶分離度只有 0.087，與 holdout 分數無關。

**比較兩個獨立訓練的模型來歸因輸入端的改動會失敗。**

第一版的查詢正規化比較訓練了兩個模型（一個用原始 query 的特徵、一個用改寫後的），得到 **−0.98%**。但檢查發現 356 個**未被改寫**的 query 也移動了（106 個變差、112 個變好）— 未改寫的 query 特徵完全相同，NDCG 差異必須為 0。差異來自兩組樹結構不同，也就是重訓雜訊。

固定模型、只更換輸入特徵後，效果從 −0.98% 收斂到 −0.06%，且 356 個未改寫 query 的差異精確為 0。
該檢查已寫入報告的 `sanity_check` 欄位，任何未來的輸入端歸因實驗都應保留同樣的閘門。

## 線上設定的兩個風險

量測過程順帶暴露的問題，與評測框架無關但同樣重要：

**延遲。** 查詢正規化在每個搜尋請求上同步呼叫 Bedrock，`app/query_normalizer.py` 的 `read_timeout` 是 2.0 秒。實測 p95 為 2,094.6 ms，代表超過 5% 的線上請求會逾時、落回 deterministic fallback 並標記 degraded。

**速率上限。** 每個請求一次 Bedrock 呼叫，在評審持續呼叫 API 的情境下必然超過每秒 1 個請求的限制。離線批次已用 1.05 秒間隔的限流器處理（實測 0.7604 RPS），線上路徑尚未。
